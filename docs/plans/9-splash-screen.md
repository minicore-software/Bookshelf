## 1. Context

- `resources/splash-screen.svg` is a 1080x1920 (9:16) full-bleed, fully opaque scene: a wall with gradients and a vignette, a shelf with books and a plant (filters `wallShadow` = feGaussianBlur/feOffset/feComponentTransfer/feMerge and `bookShadow` = feDropShadow), and a sun with hills. It also contains a gold star/rule ornament and the wordmark **as live `<text>`**: `font-family="'Georgia', 'Playfair Display', serif"`, bold, 86px, letter-spacing 2.5, fill `#1C3A2F`.
- Epic decisions this plan implements and does not revisit: D7 (the platform splash cannot show this artwork, hence two stages), D15 (assets are generated by code), D17 (Cartio's two-stage pattern), D18 (no pre-31 fallback; `androidx.core:core-splashscreen` covers minSdk 29 and up), D19 (600ms).
- Reference implementation, Cartio: `Theme.Cartio.Splash` (parent `Theme.SplashScreen`) is set on the activity in the manifest. `installSplashScreen()` runs before `super.onCreate()`. `setContent` gates on `var splashCompleted by rememberSaveable { mutableStateOf(false) }`. `CartioSplashScreen` = `LaunchedEffect(Unit) { delay(600); onComplete() }` + a full-size `Image(painterResource(R.drawable.splash_screen), contentScale = FillBounds)`.
- Current state on `origin/main`: #7 delivered `MainActivity` (Hilt, `enableEdgeToEdge()`, `MaterialTheme { Surface { BookshelfNavGraph(rememberNavController()) } }`) and a Home placeholder route. #8 delivered `@mipmap/ic_launcher` (adaptive) and `values/ic_launcher_background.xml` = `#F3EEE3`. **That file is owned by `tools/launcher-icon/generate.mjs`, and its `check` mode compares it byte for byte**, so this ticket must not edit or rename it.
- `core-splashscreen` is **not yet** in `libs.versions.toml`/`app/build.gradle.kts`, but `CLAUDE.md` already lists it in the stack (Core SplashScreen 1.2.0). Cartio pins the same version.

## 2. Key decisions

| # | Decision | Why |
|---|---|---|
| S1 | **Rasterize to PNG. No VectorDrawable.** | Same constraint as #8's K1: VectorDrawable has no blur or filter primitive, and the scene relies on two blur-based shadows plus a radial vignette with stop opacity. VectorDrawable also cannot render `<text>`. Converting the text to paths would still need a font (see S3). |
| S2 | **New tool `tools/splash-screen/`** (own `package.json` + lockfile, `@resvg/resvg-js` pinned to **2.6.2**, `generate` and `check` scripts). It mirrors `tools/launcher-icon/` and does not extend it. | It matches the established pattern (one script per source SVG, generated assets committed, Gradle never runs Node). Each tool's `check` stays focused on its own outputs. Rejected alternative: merge both into one `tools/assets/` package. That means less duplication (`decodePng`, `readPngDimensions`, writers), but it reworks #8's merged tool for no functional gain. Do it later if a third asset appears. |
| S3 | **Bundle a pinned OFL font: Playfair Display Bold (static TTF).** Render with `loadSystemFonts: false`. | **Spike finding (resvg 2.6.2): when no matching font is available, resvg drops the wordmark without any error.** The output is the scene with no "Bookshelf" text (0 wordmark pixels with system fonts off, 10,880 with Windows' Georgia). Depending on system fonts makes the output machine-dependent: Georgia is proprietary, exists on Windows/macOS and not on Linux, and the PNGs would differ by machine. So `check` would give false drift. Playfair Display is the SVG's own declared second choice and is OFL-licensed, so it may be committed. In the spike the static Bold rendered the wordmark at the designed weight and position (bbox x 335..754, y 268..335 vs Georgia's 311..779, 270..335). **The variable font `PlayfairDisplay[wght].ttf` must not be used:** resvg 2.6.2 renders only its default Regular instance, which visibly loses the bold. The font is a build-time tool input only and never ships in the APK. |
| S4 | **Five density-bucketed PNGs** `drawable-{mdpi..xxxhdpi}/splash_screen.png`, sized at 360x640dp: 360x640, 540x960, 720x1280, 1080x1920, 1440x2560. | Each device decodes a bitmap close to its own screen size. Memory at xxhdpi is about 8.3MB, and an mdpi device does not decode a 14.7MB xxxhdpi bitmap. Images stay sharp on 1440p panels. Spike sizes: 131 / 231 / 343 / 585 / 850 KB, about 2.1MB in total before AAPT2 crunch. Rejected: a single `drawable-nodpi` 1080x1920 (585KB). It is smaller, but upscaled on 1440p screens and over-decoded on low densities. Rejected: WebP. It needs a second encoder dependency (`sharp`). Revisit if APK size matters. |
| S5 | **New hand-owned palette file `values/colors.xml` with `<color name="paper">#F3EEE3</color>`.** Every splash surface references `@color/paper` (XML) or `colorResource(R.color.paper)` (Compose). `ic_launcher_background` stays as #8 generates it. | This settles the ticket's "to settle during implementation" item. `paper` is a product palette token (CLAUDE.md Design Reference), so it gets a general name in a general file. This ticket is its first consumer outside the icon. `ic_launcher_background` is a launcher-specific, generator-owned name. Renaming it or pointing it at `@color/paper` would break #8's byte-for-byte drift check and its `BACKGROUND_COLOR` constant (which also feeds the legacy PNG composites). The two tokens holding the same value is guarded by a test (section 9, FF3), not by aliasing. Rejected: reuse `@color/ic_launcher_background` for the splash. It would couple the splash and the app palette to a launcher-icon artifact name. Rejected: a Kotlin `Color(0xFFF3EEE3)` constant. It would be a second source of truth beside the XML. A Compose theme/palette file belongs to the theming work, not this ticket. |
| S6 | **`Theme.Bookshelf` gets `android:windowBackground = @color/paper`.** | It protects the "no flicker" AC. After the system splash is dismissed, any frame not yet covered by Compose shows the post-splash theme's window background. In M3 Light that is near-white, which would flash between paper and the artwork. Paper is the app's base surface colour anyway (design canvas). Compose content covers it everywhere, so nothing else is affected. |
| S7 | **Keep `ContentScale.FillBounds`** as the ticket says. | It is explicit ticket scope and the Cartio pattern. See risk R1: on 20:9 phones the artwork stretches vertically by about 25%. `ContentScale.Crop` is the one-line alternative if the device review rejects the stretch. That change belongs to the user, not to this plan. |
| S8 | **Splash composable lives in `features/splash/ui/BookshelfSplashScreen.kt`**, per the epic's Part 3 notes and Cartio's layout. | It is a UI-only feature with no domain or data layers. No ViewModel: the only state is the one-shot `splashCompleted` flag, and `rememberSaveable` handles that correctly (section 6). |

## 4. Converting the artwork: `tools/splash-screen/`

```
tools/splash-screen/
 ├── package.json          "type": "module", scripts generate/check, devDependencies { "@resvg/resvg-js": "2.6.2" } (exact pin, no caret)
 ├── package-lock.json
 ├── generate.mjs
 └── fonts/
      ├── PlayfairDisplay-Bold.ttf   static Bold instance (NOT the variable [wght] file)
      └── OFL.txt                    the font's SIL Open Font License, committed beside it
```
Add `tools/splash-screen/node_modules/` and `tools/splash-screen/out/` to the root `.gitignore`, next to the launcher-icon entries.

**Font source:** the static Bold TTF from the Google Fonts Playfair Display family download (`static/PlayfairDisplay-Bold.ttf`), with its `OFL.txt`. The fontsource `latin-700-normal.ttf` build (`cdn.jsdelivr.net/fontsource/fonts/playfair-display@latest/latin-700-normal.ttf`) was used in the spike and is an acceptable OFL-equivalent subset. Whichever file is committed, record its SHA-256 as the `FONT_SHA256` constant in `generate.mjs`.

**`generate.mjs` behaviour.** It mirrors `tools/launcher-icon/generate.mjs`: same structure, LF-normalized text writes, a `generate|check` CLI and the header comment "do not hand-edit generated outputs".

Constants:
```js
const SOURCE_SVG = join(ROOT_DIR, 'resources', 'splash-screen.svg');
const SOURCE_SIZE = { width: 1080, height: 1920 };
const FONT_PATH = join(SCRIPT_DIR, 'fonts', 'PlayfairDisplay-Bold.ttf');
const FONT_SHA256 = '<hash of the committed file>';
const BASE_DP = { width: 360, height: 640 };
const DENSITIES = [ mdpi 1, hdpi 1.5, xhdpi 2, xxhdpi 3, xxxhdpi 4 ];  // same table as launcher-icon
// output: app/src/main/res/drawable-<density>/splash_screen.png
```

Render options. These are load-bearing: each one enforces determinism.
```js
new Resvg(svgText, {
  fitTo: { mode: 'width', value: BASE_DP.width * scale },
  font: {
    loadSystemFonts: false,
    fontFiles: [FONT_PATH],
    defaultFontFamily: 'Playfair Display',
  },
});
```
- Pass the SVG through unmodified. Do not rewrite its `font-family`. The script asserts the source still has a 1080x1920 `viewBox` and fails loudly if it changes, because a re-proportioned artwork would invalidate the bucket sizes.
- Before rendering, verify the font file's SHA-256 against `FONT_SHA256`. A mismatch is a hard error.
- `generate` writes the five PNGs (`asPng()`). It also writes `out/preview.png` (the xxhdpi render) for eyeballing. The `out/` folder is git-ignored.

**`check` mode (fitness function, exits non-zero on failure):**
1. The source has `viewBox="0 0 1080 1920"`, and the font file hash matches.
2. Each `drawable-<density>/splash_screen.png` exists at exactly `360*s x 640*s` px.
3. **Opaque:** every pixel of every committed PNG has alpha 255, so the image is truly full-bleed and nothing shows through.
4. **Wordmark present:** in the band source-x 300..780, y 250..360 (scaled per density), count pixels with R<60, G<90, B<80. The count must exceed 50% of the xxhdpi reference (spike value: 9,180 at 1080px wide with Playfair Bold), scaled by s^2. This catches the silent text-drop failure (S3). The spike count was 0 when the font was missing.
5. **Drift:** re-render each density and compare it with the committed PNG, per channel, tolerance 1, reusing #8's `comparePixels`/`decodePng` approach.

Run it from `tools/splash-screen`: `npm ci && npm run generate`, then `npm run check`. There is no CI in the repo, so the developer runs `check` before every commit that touches the splash assets. The `tools/launcher-icon` check must still pass too.

## 5. Custom splash (stage 2): `BookshelfSplashScreen`

`app/src/main/java/com/minicore/bookshelf/features/splash/ui/BookshelfSplashScreen.kt`:

```kotlin
package com.minicore.bookshelf.features.splash.ui

import androidx.compose.foundation.Image
import androidx.compose.foundation.background
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.fillMaxSize
import androidx.compose.runtime.Composable
import androidx.compose.runtime.LaunchedEffect
import androidx.compose.runtime.getValue
import androidx.compose.runtime.rememberUpdatedState
import androidx.compose.ui.Modifier
import androidx.compose.ui.layout.ContentScale
import androidx.compose.ui.platform.testTag
import androidx.compose.ui.res.colorResource
import androidx.compose.ui.res.painterResource
import com.minicore.bookshelf.R
import kotlinx.coroutines.delay

internal const val SPLASH_DURATION_MS = 600L
const val SPLASH_SCREEN_TEST_TAG = "bookshelf_splash_screen"

@Composable
fun BookshelfSplashScreen(
    onComplete: () -> Unit,
    modifier: Modifier = Modifier,
) {
    val currentOnComplete by rememberUpdatedState(onComplete)

    LaunchedEffect(Unit) {
        delay(SPLASH_DURATION_MS)
        currentOnComplete()
    }

    Box(
        modifier = modifier
            .fillMaxSize()
            .background(colorResource(R.color.paper))
            .testTag(SPLASH_SCREEN_TEST_TAG)
    ) {
        Image(
            painter = painterResource(R.drawable.splash_screen),
            contentDescription = null,
            modifier = Modifier.fillMaxSize(),
            contentScale = ContentScale.FillBounds
        )
    }
}
```
Differences from Cartio, all deliberate and small:
- The `paper` background `Box` makes the Compose stage's own background resolve to the same token as the system splash (the ticket's settle item). The artwork is opaque and covers it completely. The Box is there for the first-frame and edge cases.
- `rememberUpdatedState` keeps a recomposition with a new lambda from calling a stale `onComplete`. It is the idiomatic `LaunchedEffect(Unit)` + callback form.
- The test tag lets component and activity tests find the splash.
- `contentDescription = null`: the splash is decorative and shows for 600ms. The landing screen carries the accessible "Bookshelf" title (epic D9). Do not add a TalkBack announcement.
- `painterResource` decodes the PNG synchronously during the first composition. The system splash stays up until the first frame is drawn, so the decode time is hidden behind stage 1 and no blank frame appears. Do not move this to async loading (Coil etc.), which would create exactly the flicker the AC forbids.
- Add a `@Preview` (name "Splash", `showSystemUi = true`) with `onComplete = {}`.

## 6. `MainActivity` gating

```kotlin
@AndroidEntryPoint
class MainActivity : ComponentActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        installSplashScreen()
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()
        setContent {
            MaterialTheme {
                var splashCompleted by rememberSaveable { mutableStateOf(false) }

                if (!splashCompleted) {
                    BookshelfSplashScreen(onComplete = { splashCompleted = true })
                } else {
                    Surface(modifier = Modifier.fillMaxSize()) {
                        BookshelfNavGraph(rememberNavController())
                    }
                }
            }
        }
    }
}
```
- `installSplashScreen()` comes **before** `super.onCreate()`. The import is `androidx.core.splashscreen.SplashScreen.Companion.installSplashScreen`. Do not use `setKeepOnScreenCondition`: there is no async work to wait on, and the 600ms belongs to stage 2.
- The splash sits outside the `Surface` (it paints its own full-bleed background). The nav graph and `rememberNavController()` are created only after the splash, inside the `else` branch, exactly as in Cartio.
- `enableEdgeToEdge()` stays, so the artwork draws behind the status and navigation bars (full-bleed). Do not add insets padding to the splash.
- Behaviour of `rememberSaveable`: after a rotation or other configuration change the flag stays `true`, so the splash does not replay. If the app process dies and the activity is restored from saved state, the flag is restored and the splash is skipped. That is correct, because it is not a cold start from the launcher. On API 29-30, pressing back on the root activity finishes it, so the next launch shows both stages again. On API 31+, back moves the task to the background, so returning is a warm start with no stage 2. Both are expected.
- Leave the Home placeholder untouched. The landing screen is #10's job.

## 8. Quality attributes

| Attribute | How the design serves it |
|---|---|
| **Visual fidelity / consistency** | Gradients and both blur shadows are rasterized exactly. The wordmark uses a pinned font. One `paper` token drives the system splash background, the icon plate, the Compose splash background and the window background. |
| **Perceived startup / no flicker** | The system splash covers the synchronous first-frame decode. Window background = paper means no near-white gap. Splash and nav graph are swapped in one composition, with no intermediate empty frame. |
| **Determinism / operability** | Generated assets come from a pinned renderer and a pinned font with system fonts disabled. `check` detects drift and silent text loss. |
| **Memory / size** | Density buckets bound the decoded bitmap to the device's density (about 8.3MB at xxhdpi). About 2.1MB of PNG is accepted, with WebP as a documented later lever. |

## 13. Security notes

There is no new entry point, data flow, permission, network access or stored data. The only new inputs are a committed font file, pinned by SHA-256 in the script, and the existing SVG. Both are dev-time only, and only rendered pixels ship in the APK. The font is OFL, so its `OFL.txt` must be committed beside it.

## 14. Risks for QA to probe

- **R1 Aspect stretch (FillBounds).** The 9:16 artwork on a 20:9 phone (1080x2400, edge-to-edge) is stretched about 1.25x vertically, so the wordmark and sun look taller. In landscape or on tablets (orientation is not locked) the distortion is severe: horizontal 2.4x, vertical 0.83x. This is per ticket scope. If the user rejects it during device review, change it to `ContentScale.Crop` (one line). On 20:9 portrait that crops about 108 source px per side, which trims only about 8px off each shelf end and keeps the wordmark, books and plant whole. Landscape remains a known limitation either way.
- **R2 Silent wordmark loss.** Covered by FF1 check 4. QA should still view `out/preview.png` and the xxxhdpi PNG.
- **R3 Status-bar contrast.** `enableEdgeToEdge()` with default `SystemBarStyle.auto` follows the system dark-mode setting, not the app's light theme. With the device in dark mode, the status-bar icons are light over the light wall art for 600ms. This is cosmetic and inherited from #7's setup. Note it if seen; fixing it belongs to theming.
- **R4 Colour step at the stage 1 to stage 2 hand-off.** The system splash is flat `#F3EEE3`, while the artwork's wall gradient runs `#FAF6EE` to `#E2D8C3`, so a slight tone change at the swap is inherent to the design and is not a flicker. A white or black frame is a bug.
- **R5 Restore paths.** Rotation during the 600ms (the splash should finish once, with no double navigation). Backgrounding during the splash and returning. "Don't keep activities" developer option. Process death (`adb shell am kill` while backgrounded): the splash should be skipped on restore.
- **R6 API 29-30 compat path.** `installSplashScreen()` swaps to `postSplashScreenTheme`. Verify that the icon is not clipped or doubled on the emulated splash, and that the window background stays paper (S6).
- **R7 Low-memory or low-density emulator.** Cold-start on an mdpi/hdpi AVD to confirm the right bucket loads and nothing hits an OOM.

## 16. Known Deviations

Section 12's test strategy for AC3 called for driving `BookshelfSplashScreenTest`
with `composeRule.mainClock.autoAdvance = false` and `advanceTimeBy(599)` /
`advanceTimeBy(1)` to deterministically control the `delay(600)` inside
`BookshelfSplashScreen`'s `LaunchedEffect`. In practice this did not hold up:

- With `mainClock.autoAdvance = false` and explicit `advanceTimeBy(...)` calls,
  the `delay()`-based effect still resolved as soon as any Compose test
  synchronization point ran (e.g. `onNodeWithTag(...).assertExists()`), rather
  than only after the requested virtual-time advance. The effect completed in a
  single `advanceTimeBy` call regardless of the millis passed in.
- With `autoAdvance` left at its default (`true`), the same thing happened:
  idling/sync points drained the effect immediately.
- In both cases, "immediately" was measured against the real clock, not literal
  zero: a mutation of the delay down to 100ms produced measured elapsed times
  around ~239ms (test-environment overhead), not the ~600ms the virtual-time
  plan expected and not ~0ms either. This is what revealed the mismatch — the
  virtual clock was not actually gating the effect the way `advanceTimeBy`
  implies it should.

Given this, the shipped tests (`BookshelfSplashScreenTest`) assert timing on the
real/wall clock instead, measuring `System.nanoTime()` from first composition to
`onComplete`, with an exact lower bound (`elapsedMs >= SPLASH_DURATION_MS`, since
a real `delay(600)` cannot resolve earlier than that) and a generous upper bound
(`elapsedMs < SPLASH_DURATION_MS + 1_000`) to absorb test-environment scheduling
jitter. The `onNodeWithTag(...).assertExists()` call used as a sync point does
not resolve the delay for free — it still costs real wall-clock time — so it does
not make the measurement meaningless, just subject to normal device/CI jitter.
